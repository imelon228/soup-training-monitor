# 1. PRODUCT CONTEXT

Soup — open-source toolkit и CLI для post-training больших языковых моделей (LLM). Официальный сайт позиционирует продукт вокруг цикла decide, train, ship, operate и secure; акцентирует локальное обучение на доступном оборудовании, проверку данных и конфигурации до запуска, а также проверяемый вердикт SHIP / DON'T-SHIP после обучения. Не описывай Soup как сервис аренды облачных GPU: это не соответствует текущему позиционированию официального сайта. Сценарий дорогого GPU run за $500 ниже является сценарием из take-home задания для оценки интерфейса мониторинга, а не утверждением о бизнес-модели Soup.

Разработай Training Run Monitor — frontend-платформу для мониторинга процесса обучения AI-моделей.

Пользователь запускает обучение модели и хочет отслеживать:

- Как изменяется ошибка модели (Loss).
- Как меняется скорость обучения (Learning Rate).
- Насколько стабильны градиенты (Gradient Norm).
- Есть ли аномалии или проблемы в процессе обучения.
- Стоит ли продолжать обучение или необходимо дополнительно исследовать проблему.

Ключевой пользовательский сценарий:

В сценарии этого take-home пользователь отслеживает дорогой GPU run, стоимость которого может составлять $500. Это постановка задачи мониторинга из задания Soup; не делай из неё маркетинговое утверждение, что официальный продукт Soup продаёт облачные GPU-инстансы.

Он открывает dashboard и должен иметь возможность оценить состояние обучения, опираясь на достоверные метрики.

Основная продуктовая концепция:

**A chart that looks right and a chart that is truthful are not the same thing.**

Красивый график не должен скрывать проблемы в исходных данных. Нельзя жертвовать достоверностью ради визуальной плавности, производительности или привлекательности интерфейса.

Приложение должно помогать человеку принимать обоснованные решения, а не автоматически утверждать, что обучение обязательно нужно продолжить или остановить.

Необходимо визуально выделять аномалии, некорректные данные и ограничения отображения.

# 4. DATA GENERATION — 20 TRAINING RUNS

Данные необходимо генерировать самостоятельно. Подключение к backend или реальному GPU не требуется.

Создай генератор, который формирует ровно 20 уникальных training runs.

Каждый run должен содержать:

- `id`
- `name`
- `model`
- `status`
- `createdAt`
- `duration`
- `totalSteps`
- `step`
- `loss`
- `lr`
- `grad_norm`

Основные метрики:

- `step` — номер шага обучения.
- `loss` — значение функции потерь.
- `lr` — learning rate.
- `grad_norm` — gradient norm.

В генераторе должны присутствовать как нормальные, так и намеренно испорченные данные.

ОБЯЗАТЕЛЬНЫЕ СЛУЧАИ:

### A. Normal training runs

Создай несколько запусков с реалистичными синтетическими последовательностями.

Например:

- Loss постепенно уменьшается.
- Learning Rate остаётся постоянным или меняется по scheduler.
- Gradient Norm колеблется в определённом диапазоне.

Не делай все графики одинаковыми. Добавь разнообразие.

### B. NaN and Infinity

В нескольких запусках намеренно размести:

- `NaN` в Loss.
- `Infinity` в Loss.

При необходимости добавь `-Infinity` для проверки обработки всех нечисловых значений.

### C. Duplicate steps

Создай run с несколькими записями, у которых одинаковый `step`.

Нельзя просто удалять или перезаписывать дублирующиеся записи.

### D. Unsorted steps

Создай run, в котором данные записаны не по порядку шагов.

Например:

10, 11, 15, 13, 12, 18, 17.

### E. Gaps

Создай run с намеренными пропусками между шагами обучения.

Не заполняй отсутствующие шаги искусственными значениями.

### F. One Million Points

Один из runs должен содержать ровно 1,000,000 точек.

Это обязательное условие.

Для этого запуска:

- Создай длинную последовательность шагов.
- Сгенерируй нормальную последовательность Loss.
- Добавь один экстремальный outlier spike точно в средней части временного ряда.
- Сохрани информацию о позиции этого spike.
- Не допускай других искусственных экстремальных всплесков Loss в данном тестовом сценарии.
- Проверь, что алгоритм downsampling не удаляет этот spike.

Для этого набора данных желательно использовать Typed Arrays (`Float64Array`), чтобы уменьшить overhead JavaScript-объектов.

### G. Deterministic generation

Генерация должна быть воспроизводимой.

Используй seeded random generator, чтобы при каждом запуске приложения и тестов можно было получить одинаковые данные.

Реализуй генерацию отдельно от React UI.

Результат:

В приложении должно отображаться 20 запусков с различными характеристиками, включая все перечисленные дефектные случаи.

# 7. DATA NORMALIZATION AND INTEGRITY

Это одна из наиболее важных частей задания.

Создай отдельный модуль для обработки данных до их передачи в графики.

Пример:

`src/utils/normalizeData.ts`

Основные требования:

## 7.1. Non-finite values

Обрабатывай:

- NaN.
- Infinity.
- -Infinity.

Критически важно:

NaN и Infinity никогда не должны преобразовываться в 0.

Необходимо:

1. Сохранять исходные данные.
2. Выявлять некорректные значения.
3. Считать количество некорректных записей.
4. Не передавать их в график как обычные числовые значения.
5. Представлять их как разрывы линии (`null` или эквивалент).
6. Использовать `connectNulls: false`, если это соответствует выбранной конфигурации графика.
7. Показывать соответствующее предупреждение в UI.

Не допускай ситуации, в которой приложение визуально сглаживает или скрывает ошибочные значения.

## 7.2. Unsorted steps

Данные должны быть отсортированы по Step перед построением последовательности.

Используй stable sorting.

Сохраняй исходный индекс каждой точки, чтобы можно было восстановить происхождение записи.

## 7.3. Duplicate steps

Нельзя молча удалять записи с одинаковым Step.

Не используй простое перезаписывание через Map, которое оставляет только одну точку.

Разработай явную стратегию обработки дублирующихся шагов:

- Сохраняй все оригинальные значения.
- Выявляй группы дубликатов.
- Отображай предупреждения.
- Не усредняй конфликтующие значения без явного указания, что это производная метрика.
- Не соединяй значения на одном Step таким образом, чтобы визуально создать ложную последовательность обучения.

Предпочтительный вариант визуализации — показывать диапазон значений для повторяющегося Step с помощью маркера или отдельного визуального индикатора.

При hover пользователь должен иметь возможность увидеть все исходные значения этого шага.

Зафиксируй выбранную стратегию в документации и тестах.

## 7.4. Missing steps / Gaps

Не интерполируй отсутствующие значения автоматически.

Если между шагами существует разрыв:

- Выявляй его.
- Сохраняй информацию о пропущенном диапазоне.
- Не создавай фиктивные точки.
- Не показывай сглаживание через отсутствующие данные как будто измерения существуют.

Для синтетических данных используй известный expectedStepInterval.

Если промежуток между двумя существующими измерениями нарушает установленное правило обнаружения пропусков, отображай разрыв или отдельную индикацию.

Не предполагай, что любой пропуск между соседними integer values является ошибкой без учёта ожидаемого интервала.

# 8. DOWNSAMPLING — MILLION-POINT PERFORMANCE

Это наиболее важная алгоритмическая задача проекта.

Нельзя напрямую отрисовывать все 1,000,000 точек при каждом обновлении графика.

Но и обычное удаление каждой N-й точки недопустимо, потому что оно может скрыть важные события.

Реализуй отдельный алгоритм downsampling.

Предпочтительный подход:

**Viewport-aware Min-Max Downsampling.**

Рассмотри реализацию Min-Max algorithm с разделением данных на buckets.

Основной принцип:

1. Определить текущую видимую область графика.
2. Определить ширину графика в пикселях.
3. Рассчитать количество buckets с учётом разрешения.
4. В каждом bucket найти minimum и maximum значения.
5. Сохранить минимум и максимум.
6. Сохранить первую и последнюю точки видимой области.
7. Сохранить критические аномалии.
8. Передавать графику только необходимое количество точек.

Ключевое требование:

**The spike must remain visible at every zoom level whenever its source point belongs to the visible viewport.**

Это означает:

- При отображении полного миллиона точек spike должен оставаться видимым.
- При приближении к области spike он должен оставаться видимым.
- При изменении ширины графика spike не должен исчезать.
- При изменении количества buckets spike не должен удаляться.
- При повторном расчёте downsampling spike должен сохраняться.

Нельзя рассчитывать на то, что обычное случайное sampling сохранит экстремальное значение.

### Дополнительные требования

- Не изменяй оригинальный набор данных.
- Downsampling должен быть детерминированным.
- Сохраняй индекс исходной точки.
- Не превращай экстремальные значения в более удобные для графика.
- Корректно обрабатывай одинаковые X coordinates.
- Обрабатывай NaN и Infinity до визуализации.
- Сохраняй границы пропущенных участков.

Если spike является единственным максимумом bucket, он обязан попасть в отображаемые данные.

При необходимости используй отдельный anomaly-preservation mechanism.

Не допускай скрытого изменения исходных метрик.

### Performance implementation

Для миллиона точек:

- Предпочитай Typed Arrays.
- Не создавай миллион React elements.
- Не запускай downsampling на каждом React render.
- Используй memoization.
- Рассмотри Web Worker для генерации и обработки больших данных.
- Используй `requestAnimationFrame` или debounce там, где это действительно необходимо.
- Не выполняй дорогостоящие операции на каждом mousemove.
- Не используй тяжёлую анимацию.
- Сохраняй небольшое количество объектов, передаваемых в chart renderer.

## Mandatory Test 1 — Spike preservation

Создай тест для миллиона точек.

Проверь, что:

- Spike сохраняется после downsampling полного набора.

- Spike сохраняется при разных viewport ranges, содержащих его.
- Spike сохраняется при различных уровнях zoom.

- Infinity не превращается в 0.
- -Infinity не превращается в 0.
- Такие значения не участвуют в обычных статистических вычислениях.
- Количество invalid values рассчитывается правильно.
- График получает разрывы, а не искусственные нулевые точки.
- Некорректные записи остаются доступными для диагностики.

## Mandatory Test 3 — Duplicate steps

Проверь:

- Дубликаты обнаруживаются.
- Исходные значения не перезаписываются.
- Значения не усредняются молча.
- Сортировка по Step работает правильно.
- Дубликаты можно обнаружить в отображаемых данных.

## Mandatory Test 4 — Unsorted steps

Проверь:

- Неотсортированные шаги корректно сортируются.
- Исходный порядок можно восстановить по source index.
- Sorting не изменяет оригинальный массив.
- Линия графика строится в правильной последовательности.

## Mandatory Test 5 — Gaps

Проверь:

- Пропуски обнаруживаются.
- Искусственные точки не создаются.
- Пропущенные значения не интерполируются.
- В визуализации разрывы не скрываются.

## Mandatory Test 6 — Axis and numbers truthfulness

Проверь:

- Axis labels соответствуют исходным числовым значениям.
- Tooltip показывает корректные значения.
- Не происходит незаметного масштабирования или изменения исходных данных.
- Значения не округляются перед проведением расчётов.
- Форматирование чисел не приводит к потере точности в tooltip.

## Mandatory Test 7 — Summary metrics

Проверь:

- Initial Loss.
- Last Finite Loss.
- Minimum Loss.
- Valid Points.
- Invalid Points.
- Current Learning Rate.
- Current Gradient Norm.

Особенно проверь случаи, когда последняя запись содержит NaN или Infinity.

## Mandatory Test 8 — Edge cases

Проверь:

- Empty dataset.
- One data point.
- All points are NaN.
- All points are Infinity.
- Duplicate X values.
- Large gaps.
- Zero values.
- Negative values, если они допустимы выбранной метрикой.

Не ограничивайся только тестами на успешные сценарии.

В конце необходимо запустить весь набор тестов и показать реальный результат.

Не указывай фиктивное количество passing tests.

# 10. SILENT FAILURES

Отдельно обработай каждую проблему, указанную Soup.

## 10.1. Stale data

Проблема:

После переключения между двумя runs пользователь может увидеть старые данные.

Решение:

- Отслеживай ID текущего run.
- Сбрасывай или корректно обновляй состояние при смене маршрута.
- Не отображай данные предыдущего run как новые данные.

## 10.2. Request race condition

Смоделируй асинхронную загрузку данных через локальный data service.

При быстром переключении между runs возможна ситуация, когда более старый запрос завершится позже нового.

Реализуй защиту:

- AbortController, где это применимо.
- Request ID или другой механизм контроля актуального результата.
- Применение ответа только к актуальному выбранному run.

Напиши автоматический тест, имитирующий быстрое переключение между Run A и Run B.

Проверь, что результат Run A не перезаписывает результат Run B после завершения старого запроса.

## 10.3. Locale and timezone

Обеспечь корректное отображение дат и чисел.

Используй Intl API.

Не предполагай, что любой пользователь находится в одной временной зоне или использует один формат чисел.

Внутреннее хранение timestamps должно быть однозначным, предпочтительно UTC.

В интерфейсе отображай локальное время пользователя.

Числовые метрики должны форматироваться отдельно от исходных значений.

## 10.4. Smoothing hides divergence

Не включай автоматическое сглаживание, способное скрывать реальные скачки и нестабильность.

Если предлагаешь smoothing:

- Он должен быть опциональным.
- Исходная линия должна оставаться доступной.
- Пользователь должен понимать, какая линия отображает оригинальные данные.
- Сглаживание не должно подменять данные в summary или tooltip.

## 10.5. Log scale with zeros

Логарифмическая шкала не может корректно отображать нулевые и отрицательные значения.

Поэтому:

- Default scale — Linear.
- Добавь возможность переключения на Log Scale, только если она корректно реализована.
- Проверь исходные значения.
- Если существуют нули или отрицательные значения, не допускай незаметного удаления точек.
- Покажи предупреждение и объясни, почему Log Scale недоступна.
- Не заменяй нули на искусственные положительные значения.

Если библиотека не позволяет безопасно решить проблему, лучше временно отключить Log Scale, чем показывать искажённые данные.

## 10.6. Additional silent failures

Проверь:

- Переход между runs во время загрузки.
- Несовместимость данных после изменения фильтров.
- Повторные вычисления при каждом render.
- Incorrect memoization.
- Некорректные значения после преобразования в JavaScript Number.
- Ошибки при работе с пустыми наборами данных.
- Неправильное форматирование очень больших и очень маленьких значений.

Создай отдельный раздел документации, описывающий каждый обнаруженный silent failure и способ его проверки.
